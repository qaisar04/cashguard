# CashGuard — проверка кассовой дисциплины по видео

Решение кейса ForteBank (Datathon 26). Пользователь загружает видео с камеры над рабочим местом кассира, сервис
возвращает вердикт (`violation` / `no_violation`) и для каждого возможного нарушения — тип, таймкод, описание того,
что видно на видео, 1–3 кадра-доказательства и ссылку на нормативный акт НБРК с номером пункта.

Вся обработка локальная: модели работают внутри сервиса, облачные AI-сервисы не используются, лица не распознаются,
звук не анализируется. Результат — подсказка для проверяющего, а не юридическое или дисциплинарное заключение.

## Доступ для жюри

| | |
|---|---|
| Веб-интерфейс | https://durham-struck-recipes-composer.trycloudflare.com |
| API | https://durham-struck-recipes-composer.trycloudflare.com/api/v1 |
| Ключ | передан в форме сдачи; заголовок `X-API-Key` |

```bash
curl -X POST https://durham-struck-recipes-composer.trycloudflare.com/api/v1/analyze \
  -H "X-API-Key: <ключ>" -F "file=@video_017.mov"
# {"job_id":"3f2a9c1e","status":"processing"}

curl https://durham-struck-recipes-composer.trycloudflare.com/api/v1/jobs/3f2a9c1e -H "X-API-Key: <ключ>"
# {"job_id":"3f2a9c1e","status":"done","verdict":"violation","violations":[{"type":"Сейф оставлен открытым",
#   "timecode_sec":5.0,"description":"С 5 с по 11 с дверца сейфа открыта… Нормативный источник: …, п. 74, п. 77.",
#   "evidence_frames":[{"timestamp_sec":5.0,"image_base64":"/9j/…"}]}]}
```

- Принимаются `.mov` и `.mp4`. Запрос без ключа или с неверным ключом — 401.
- Статусы задачи: `processing`, `done`, `failed`. Ответ — ровно по схеме раздела 10 ТЗ.
- Видео обрабатываются по очереди одним обработчиком; одно видео — обычно 15–40 с. Если отправить несколько
  сразу, каждое следующее ждёт окончания предыдущих.

## Запуск

### Docker (перенос в контур банка)

```bash
cp .env.example .env            # задайте CASHGUARD_API_KEY (ключ для внешних клиентов) и ML_API_KEY (внутренний)
docker compose up --build       # первая сборка скачивает веса (~1.7 ГБ) и сохраняет их в образ
open http://localhost:8080      # API_PORT=8090 — если порт 8080 занят
```

После сборки интернет не нужен: веса и прототипы лежат внутри образа, сервис работает в режиме
`HF_HUB_OFFLINE=1`.

Скорость: в Docker на macOS видеокарта недоступна, модели работают на CPU — около 7 с на кадр, ролик на 145 с
не укладывается в 5 минут. Для такой нагрузки нужен Linux-хост с GPU (CUDA выбирается автоматически) или
нативный запуск на Mac.

### Нативно (так работает сервис для жюри)

```bash
cd ml && python3.12 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/python scripts/download_weights.py         # один раз, дальше офлайн
HF_HUB_OFFLINE=1 ML_API_KEY=<внутренний ключ> .venv/bin/uvicorn app.main:app --port 8000

cd api && CASHGUARD_API_KEY=<ключ> ML_API_KEY=<внутренний ключ> ./mvnw spring-boot:run
```

На Mac M1 модели работают через MPS: около 0.8 с на кадр. Публичный адрес — Cloudflare Tunnel на порт 8080
(`cloudflared tunnel --url http://localhost:8080`).

### Проверка и отладка

```bash
cd api && ./mvnw test                     # тесты Spring
cd ml && .venv/bin/pytest                 # тесты ML (107)
cd ml && .venv/bin/python scripts/debug_video.py ~/Downloads/open/videos/Х-22.mov --out debug/X-22
#   кадры с рамками и подписями ролей, observations.json, events.json, треки людей
```

## Архитектура

```
браузер / жюри ──X-API-Key──▶ api (Spring Boot)                    ml (FastAPI)
                               POST /api/v1/analyze → job_id       POST /infer {video_path}
                               GET  /api/v1/jobs/{id}   ──────▶    кадры (1/с) → детекторы и классификаторы →
                               очередь, таймаут 270 с,             треки людей и роли → состояние на каждую
                               ответ по схеме ТЗ, веб-интерфейс    секунду → правила → события + кадры
                               └──────── общий каталог ./data (видео) ────────┘
```

- **api** (Java 17, Spring Boot 3.5) — всё, что видит внешний клиент: ключ, загрузка, очередь, статусы, строгая
  схема ответа, веб-интерфейс. Если ML не ответил за 270 с, задача получает `failed`, а не зависает — запас до лимита
  в 5 минут.
- **ml** (Python 3.12, FastAPI) — только анализ. Конвейер:
  1. кадры раз в секунду (не больше 150 на ролик);
  2. детекторы находят людей, ноутбук, наличные, сумки, личные вещи, напитки, стекло, счётную машину;
  3. классификаторы определяют состояние экрана, сейфа и двери;
  4. треки людей: кто кассир, кто посетитель, кто отражение в стекле или человек в коридоре;
  5. состояние сцены на каждую секунду;
  6. правила — по одному модулю на тип нарушения (`ml/pipeline/rules/`);
  7. кадры-доказательства с рамками и нормативная ссылка из `ml/rules/rules.json`.
- Все пороги — в `ml/config.yml`, каталог типов и пунктов — в `ml/rules/rules.json`.

### Модели

| Назначение | Модель | Лицензия |
|---|---|---|
| Люди, ноутбук, сумки, личные вещи, напитки | `PekingU/rtdetr_r50vd_coco_o365` (RT-DETR) | Apache-2.0 |
| Наличные, сумки и папки, стекло, счётная машина (поиск по текстовому описанию) | `google/owlv2-base-patch16-ensemble` (OWLv2) | Apache-2.0 |
| Состояние экрана, сейфа, двери; «человек в комнате / отражение / за стеклом» | `openai/clip-vit-base-patch32` (CLIP) | MIT |

- Состояния экрана, сейфа и двери определяются сравнением с размеченными примерами из датасета (`ml/prototypes/*.npz`):
  экран — 172 примера, сейф — 138, дверь — 113. Классификатор отвечает «не знаю», если кадр не похож ни на один пример.
- Работает ли счётная машина — без модели: по изменению изображения внутри её рамки между соседними кадрами.
- Отражения в стеклянной стене отсекаются: трек, повторяющий движение другого человека зеркально, или трек, который
  не выходит из полосы стекла, не считается человеком в комнате.
- В конфиге есть VLM `Qwen/Qwen3-VL-2B-Instruct` (Apache-2.0), но он **выключен**: на датасете нашёл 1 из 6 «денежных»
  нарушений и не укладывался по времени.

## Распознаваемые нарушения

| type_id | Название | Когда срабатывает |
|---|---|---|
| `workstation_unlocked` | Рабочая станция не заблокирована при уходе кассира | Кассира нет на месте ≥ 3 с, на экране — рабочее приложение или рабочий стол |
| `valuables_left_unattended` | Ценности оставлены без присмотра | Кассира нет на месте ≥ 3 с, на столе наличные, сумка или папка |
| `safe_left_open` | Сейф оставлен открытым | Дверца сейфа открыта ≥ 4 с, у сейфа никого нет |
| `cash_room_door_open` | Дверь кассы оставлена открытой | Дверь кассового помещения открыта ≥ 4 с |
| `unauthorized_entry` | Посторонний в помещении кассы | Входит ещё один человек, пока у стойки обслуживают клиента или после того, как дверь стояла открытой |
| `cash_exposed_to_visitor` | Наличные в открытом доступе при постороннем | Наличные лежат на столе, когда входит новый посетитель |
| `personal_items_at_workplace` | Личные вещи на кассовом столе | Сумка, рюкзак или одежда лежат на столе рядом с кассиром ≥ 4 с |
| `food_drink_at_workplace` | Еда или напитки на рабочем месте | Чашка или бутылка на столе рядом с кассиром ≥ 4 с |
| `counting_not_in_client_presence` | Пересчёт не в присутствии клиента | Счётная машина работает ≥ 2 с, а клиент, стоявший у стойки ≥ 3 с, ушёл за последние 6 с |
| `unrecounted_cash_to_safe` | Наличные убраны в сейф без пересчёта | Наличные лежали на столе ≥ 3 с, затем кассир у открытого сейфа, со стола они исчезли, счётная машина за минуту до этого не работала |
| `cash_not_machine_verified` | Наличные не проверены на счётной машине | Наличные у посетителя, а счётная машина за 15 с до и после не работала |

Таймкод отсутствия кассира — последняя секунда, когда он был на рабочем месте. В одном видео может быть до 5 событий.

Есть в каталоге, но не работают:
- `no_client_identification` (приём наличных без документа) — нужен VLM, он выключен;
- `collector_handover_unverified` (приём сумки от инкассатора без проверки) — выключен из-за ложных срабатываний.

## Нормативная база

Постановления Правления НБРК № 231 от 29.11.2019 (кассовые операции) и № 14 от 24.02.2020 (охрана и устройство
помещений). Тексты пунктов, принцип сопоставления и сила привязки каждого типа — в
[docs/normative-sources.md](docs/normative-sources.md).

## Ограничения и известные ошибки

**Не распознаётся:**
- приём наличных без предъявления документа (X-2) — документ слишком мелкий для детектора;
- выдача наличных без пересчёта (X-1, X-44) — детектор не видит наличные в руках;
- приём сумки от инкассатора без проверки (X-17) — правило выключено, давало ложные срабатывания на X-16 и X-24.

**Ложные срабатывания:** X-39 — `unauthorized_entry` на 50 с: трекер перескакивает с входящего клиента на его
отражение в стекле.

**Таймкоды:** X-47 ошибается на −7.9 с, X-30 — на +4.1 с, X-18 — на −3.9 с. X-47 побайтно совпадает с X-4, при этом
их метки различаются на 11 с.

**Другой ракурс камеры:** примеры для экрана, сейфа и двери сняты одной камерой, рамка двери задана в конфиге
(`door.anchor.fallback_box`). С другого ракурса эти признаки могут не срабатывать; для двери настроено «не знаю»
вместо ложного «открыта». Детекция людей, наличных, сумок и правила по их положению от ракурса не зависят.
Проверка на искажённых копиях (`scripts/warp_videos.py`) подготовлена, но не проводилась.

**Скорость:** без GPU (Docker на Mac, CPU-сервер) длинный ролик не укладывается в 5 минут.

**Роли «кассир / посетитель»:** определяются по тому, кто дольше всех сидит у ноутбука, а не по внешности. Если
кассир не попадает в кадр, его отсутствие может быть принято за уход с рабочего места.

**Нормативная привязка:** для части типов пункт — толкование, а не прямая норма (см. docs/normative-sources.md).
